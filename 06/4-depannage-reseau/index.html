    43. VI.4 Dépannage réseau et diagnostic client-serveur

    Une panne réseau en production interrompt l'activité des applications et des utilisateurs. L'administrateur Linux doit adopter une démarche rigoureuse pour localiser rapidement la couche défaillante plutôt que de modifier des configurations au hasard.

    Cette section présente la méthode en trois étapes, les outils de diagnostic de l'objectif LPIC-1 109.3, ainsi qu'un guide pratique complet de résolution d'incident entre un client applicatif (ex. code Java) et un serveur de base de données.

    43.1 VI.4.1 Méthodologie de gestion des pannes

    Face à un incident réseau, appliquez systématiquement ces trois phases :

    flowchart LR
    S1["1. Isoler<br/>Utiliser les outils pour<br/>déterminer les symptômes"] --> S2["2. Résoudre<br/>Corriger la cause racine<br/>identifiée"]
    S2 --> S3["3. Enregistrer<br/>Documenter la détection<br/>et la résolution"]
    1. Isoler : délimiter le périmètre (problème local à un poste, limité à un port applicatif, ou coupure réseau globale ?).
    2. Résoudre : appliquer la correction ciblée (démarrer un service, ouvrir un port pare-feu, corriger une route ou /etc/hosts).
    3. Enregistrer : consigner la procédure de détection et de résolution (documentation / ticket) pour gagner du temps lors d'un futur incident similaire.

    43.2 VI.4.2 Les outils de diagnostic réseau

    Commande Usage principal
    ip addr, ifconfig, ifup, ifdown Examiner, activer ou désactiver les interfaces réseau
    ip route, route -n, netstat -r Examiner la table de routage et la passerelle par défaut
    ping Tester l'accessibilité IP (ICMP) d'une machine et la latence
    hostname Afficher ou vérifier le nom de la machine
    host, dig, getent Diagnostiquer les problèmes de résolution DNS / /etc/hosts
    netstat, ss Statistiques d'interfaces, sockets ouvertes et processus en écoute
    traceroute, tracepath Localiser le saut (routeur) où le trafic s'interrompt
    telnet, nc (netcat) Tester l'ouverture d'un port TCP précis sur un serveur distant

    43.3 VI.4.3 Interpréter ping, traceroute et netstat

    43.3.1 VI.4.3.1 Lire les erreurs de ping

    La commande ping envoie des paquets ICMP Echo Request et attend un Echo Reply. Trois messages d'erreur permettent d'orienter immédiatement le diagnostic :

    • ping: unknown host (ou Name or service not known)
      Le nom d'hôte n'a pas pu être traduit en adresse IP. Vérifiez /etc/resolv.conf, /etc/hosts et /etc/nsswitch.conf.

    • Destination Host Unreachable
      Un routeur (ou l'hôte local faute de passerelle) signale via ICMP qu'il ne possède aucune route ou résolution ARP vers la destination.

    • 100% packet loss
      Aucune réponse reçue : la machine cible est éteinte, une route retour manque, ou un pare-feu bloque silencieusement les paquets ICMP (DROP).

    Limiter le nombre de paquets

    Sous Linux, ping s'exécute en boucle infinie jusqu'à Ctrl+C. Utilisez l'option -c (count) pour envoyer un nombre fixe de paquets : ping -c 4 192.168.1.1.

    43.3.2 VI.4.3.2 Localiser une coupure avec traceroute

    traceroute (ou tracepath, qui ne nécessite pas de privilèges root) affiche chaque routeur traversé jusqu'à la destination en faisant varier le TTL IP :

    $ traceroute mailserver1
 1  pyramid.alrac.net (10.0.1.1)  0.842 ms  0.715 ms  0.690 ms
 2  mailserver1.alrac.net (10.0.2.25)  1.924 ms  1.810 ms  1.795 ms
    Si la trace s'arrête avec des astérisques * * * après le saut N, le problème de routage ou de filtrage se situe au niveau du routeur suivant.

    43.3.3 VI.4.3.3 Analyser les interfaces et sockets avec netstat (et ss)

    La commande netstat (remplacée sur les systèmes récents par ss, plus rapide et aux options quasi identiques) offre trois vues essentielles :

    // 1. Statistiques d'erreurs sur les interfaces (colonnes ERR, DRP, OVR)
$ netstat -i

// 2. Table de routage numérique
$ netstat -rn

// 3. Toutes les sockets TCP/UDP avec le programme associé (-p nécessite sudo)
$ sudo netstat -tua -p

    Les colonnes ERR (erreurs de transmission/CRC), DRP (dropped, paquets abandonnés) et OVR (overrun, débordement de tampon) de netstat -i révèlent un problème matériel (câble défectueux, carte réseau saturée, erreur de duplex).

    43.3.3.1 VI.4.3.3.1 Inspecter les services en écoute : netstat -nlpt (ou ss -nlpt)

    Pour vérifier quels services TCP écoutent sur un serveur, l'administrateur utilise la combinaison d'options -nlpt :

    • -n : affichage numérique des IP et des ports (pas de résolution DNS lente).
    • -l : uniquement les sockets en écoute (listening).
    • -p : affiche le PID et le nom du processus (nécessite sudo).
    • -t : filtre uniquement le protocole TCP (-u pour UDP).
    $ sudo netstat -nlpt
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      892/sshd
tcp        0      0 127.0.0.1:5432          0.0.0.0:*               LISTEN      1450/postgres
tcp        0      0 0.0.0.0:3306            0.0.0.0:*               LISTEN      1612/mysqld

    Équivalent moderne avec ss :

    $ sudo ss -nlpt

    43.4 VI.4.4 Cas pratique : Diagnostiquer une panne Client (Java) ↔ Base de Données

    Scénario réel : Une application Java déployée sur le serveur applicatif srv-app n'arrive pas à se connecter à une base de données PostgreSQL (port 5432) hébergée sur srv-bdd (10.20.30.40). L'application renvoie une erreur de type UnknownHostException, Connection timed out ou Connection refused.

    Comment identifier méthodiquement la cause exacte ? Suivez cet arbre de décision couche par couche :

    flowchart TD
    Start["Erreur de connexion Java -> BDD (5432)"]:::start --> E1["1. Test résolution de nom<br/>getent hosts srv-bdd"]:::test
    E1 -->|Échec| C1["Cause : DNS ou /etc/hosts manquant"]:::cause
    E1 -->|OK : 10.20.30.40| E2["2. Test joignabilité réseau<br/>ping -c 3 10.20.30.40"]:::test
    E2 -->|Destination Unreachable / Loss| C2["Cause : Routage, passerelle, VLAN ou ICMP filtré"]:::cause
    E2 -->|OK ou ICMP filtré| E3["3. Sur srv-bdd : vérifier l'écoute<br/>sudo netstat -nlpt | grep 5432"]:::test
    E3 -->|Aucune ligne| C3["Cause : Service BDD arrêté ou crashé"]:::cause
    E3 -->|Écoute sur 127.0.0.1:5432| C4["Cause : Écoute locale uniquement<br/>(configurer listen_addresses = '*')"]:::cause
    E3 -->|Écoute sur 0.0.0.0:5432| E4["4. Depuis srv-app : test port TCP<br/>telnet 10.20.30.40 5432"]:::test
    E4 -->|Connection timed out| C5["Cause : Pare-feu DROP les paquets<br/>(iptables, ufw, firewalld, réseau)"]:::cause
    E4 -->|Connection refused| C6["Cause : Paquet atteint l'hôte mais port fermé<br/>ou pare-feu en REJECT"]:::cause
    E4 -->|Connected| C7["Réseau & Port OK !<br/>Problème applicatif (identifiants, pg_hba.conf, TLS)"]:::ok

    43.4.1 VI.4.4.1 Étape 1 : Vérifier la résolution de nom (depuis srv-app)

    Si le code Java utilise un nom d'hôte (jdbc:postgresql://srv-bdd:5432/appdb) :

    $ getent hosts srv-bdd
10.20.30.40     srv-bdd.interne srv-bdd
    • Si rien n'est retourné (et Java lève java.net.UnknownHostException) : le problème vient du DNS (/etc/resolv.conf) ou d'une entrée manquante dans /etc/hosts.

    43.4.2 VI.4.4.2 Étape 2 : Vérifier la connectivité IP et le routage (depuis srv-app)

    $ ping -c 3 10.20.30.40
    • Destination Host Unreachable : vérifiez la table de routage (ip route ou route -n) et la passerelle par défaut.
    • 100% packet loss : le serveur cible est peut-être éteint, ou un routeur intermédiaire bloque (vérifiez avec traceroute 10.20.30.40). Attention : certains pare-feux bloquent ICMP (ping) tout en autorisant le port TCP 5432 ; passez toujours à l'étape 4 pour confirmer.

    43.4.3 VI.4.4.3 Étape 3 : Vérifier le service et son adresse d'écoute (sur srv-bdd)

    Connectez-vous sur le serveur de base de données et exécutez netstat -nlpt (ou ss -nlpt) :

    $ sudo netstat -nlpt | grep 5432
tcp        0      0 127.0.0.1:5432          0.0.0.0:*               LISTEN      1450/postgres

    Trois situations se présentent :

    1. Aucune sortie : le service de base de données n'est pas démarré (sudo systemctl status postgresql) ou écoute sur un autre port.
    2. 127.0.0.1:5432 (piège très fréquent !) : le service est démarré, mais il n'écoute que sur l'interface locale (localhost). Il refusera toute connexion provenant d'un autre serveur ! Il faut modifier sa configuration (ex. listen_addresses = '*' dans postgresql.conf ou bind-address = 0.0.0.0 pour MySQL) puis redémarrer le service.
    3. 0.0.0.0:5432 (ou 10.20.30.40:5432) : le service écoute bien sur le réseau. Passez à l'étape 4.

    43.4.4 VI.4.4.4 Étape 4 : Tester le port TCP bout-en-bout avec telnet (depuis srv-app)

    La commande telnet <IP> <port> (ou nc -zv <IP> <port>) tente d'établir une poignée de main TCP (SYN → SYN-ACK → ACK) directement depuis le client vers le port cible :

    $ telnet 10.20.30.40 5432

    Les trois résultats possibles tranchent définitivement le diagnostic :

    • Connected to 10.20.30.40. (Escape character is '^]'.) :
      Le routage, le pare-feu et le port d'écoute fonctionnent parfaitement ! Si le code Java échoue encore, la cause est applicative (mauvais mot de passe, base inexistante, règle d'autorisation IP refusée dans pg_hba.conf ou GRANT MySQL, exigence TLS/SSL). (Tapez ++ctrl+altgr+right_bracket++ puis quit pour fermer telnet).

    • telnet: Unable to connect to remote host: Connection refused :
      Un paquet TCP RST a été renvoyé immédiatement. Soit le service est arrêté/écoute sur 127.0.0.1 (voir étape 3), soit un pare-feu rejette explicitement le port (REJECT).

    • Blocage silencieux puis Connection timed out :
      Aucun paquet de retour n'arrive. Un pare-feu (local sur srv-bdd via iptables/nftables/ufw/firewalld, ou un pare-feu matériel / Security Group cloud) supprime silencieusement (DROP) les paquets à destination du port 5432.

    // Vérifier rapidement le pare-feu local sur srv-bdd :
$ sudo ufw status            # Ubuntu / Debian
$ sudo firewall-cmd --list-all  # RHEL / Rocky / AlmaLinux
$ sudo iptables -L -n -v     # Règles Netfilter brutes
