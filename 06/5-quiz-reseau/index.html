    44. VI.5 Questions d'auto-évaluation

    Ce questionnaire reprend les notions clés des objectifs LPIC-1 109.1 à 109.4 ainsi que des mises en situation réelles de dépannage entre serveurs.

    1. Lors de l'encapsulation TCP/IP, dans quel ordre exact les en-têtes sont-ils ajoutés aux données applicatives avant leur transmission sur le câble réseau ?

      Réponse

      De l'intérieur vers l'extérieur (couches hautes vers couche physique) :

      1. Données applicatives
      2. En-tête Transport (TCP ou UDP) → Segment / Datagramme
      3. En-tête IP (couche Inter-réseau) → Paquet
      4. En-tête et pied de Liaison (couche 2, Ethernet) → Trame

    2. Quel fichier système permet d'associer un nom de protocole (comme tcp, udp, icmp) à son numéro IP (6, 17, 1), et quel autre fichier associe un nom de service (comme ssh, http) à son numéro de port ?

      Réponse
      • /etc/protocols : associe les noms de protocoles IP à leur numéro (tcp 6, udp 17).
      • /etc/services : associe les noms de services applicatifs à leur port et protocole de transport (ssh 22/tcp, http 80/tcp).

    3. Sur un poste Linux, le fichier /etc/nsswitch.conf contient la ligne suivante : hosts: files dns
      Vous avez ajouté 10.10.10.50 api-interne dans /etc/hosts, mais votre serveur DNS renvoie une ancienne IP 10.10.10.10 pour api-interne.

      3.1 Quelle adresse IP sera utilisée par ping api-interne ?

      Réponse

      10.10.10.50.
      La directive files précède dns dans /etc/nsswitch.conf : le système consulte d'abord /etc/hosts et s'arrête dès qu'il y trouve une correspondance.

      3.2 Quelle adresse IP affichera la commande dig api-interne et pourquoi ?

      Réponse

      10.10.10.10.
      Les outils DNS purs (dig, host) interrogent directement les serveurs déclarés dans /etc/resolv.conf et ignorent /etc/hosts. Pour tester la résolution réelle du système, il faut utiliser getent hosts api-interne.

    4. Vous exécutez route -n et obtenez la ligne suivante : 0.0.0.0 192.168.1.254 0.0.0.0 UG 100 0 0 eth0

      4.1 Que représente cette ligne ?

      Réponse

      C'est la route par défaut (default gateway) : tout trafic destiné à un réseau inconnu est envoyé vers le routeur 192.168.1.254 via l'interface eth0.

      4.2 Que signifient les drapeaux U et G ?

      Réponse
      • U (Up) : la route est active.
      • G (Gateway) : la destination est atteinte via une passerelle intermédiaire.

    5. Quelle commande moderne (iproute2) remplace ifconfig eth0 192.168.1.20 netmask 255.255.255.0 up ?

      Réponse 
      $ sudo ip addr add 192.168.1.20/24 dev eth0
$ sudo ip link set eth0 up

    6. Un développeur vous signale que son application Java sur srv-app ne parvient plus à joindre la base PostgreSQL (port 5432) sur srv-bdd (10.20.30.40).

      6.1 Vous lancez ping 10.20.30.40 depuis srv-app et obtenez Destination Host Unreachable. Où se situe le problème ?

      Réponse

      Au niveau réseau / routage (couche 3) : aucun chemin réseau ou résolution ARP ne permet d'atteindre 10.20.30.40. Il faut vérifier les interfaces (ip addr), la table de routage (ip route / route -n) et la passerelle.

      6.2 Le ping fonctionne, vous vous connectez sur srv-bdd et lancez sudo netstat -nlpt | grep 5432. Vous voyez : tcp 0 0 127.0.0.1:5432 0.0.0.0:* LISTEN 1450/postgres
      Pourquoi l'application Java distante échoue-t-elle avec Connection refused ?

      Réponse

      Le service PostgreSQL tourne, mais il écoute uniquement sur l'adresse de boucle locale 127.0.0.1. Il n'accepte donc que les connexions locales à srv-bdd et rejette toute connexion venant du réseau (srv-app). Il faut configurer l'écoute sur 0.0.0.0 ou l'IP réseau du serveur (listen_addresses = '*' dans postgresql.conf) et redémarrer le service.

      6.3 Après correction, netstat -nlpt affiche bien 0.0.0.0:5432. Depuis srv-app, vous exécutez telnet 10.20.30.40 5432, qui reste bloqué plusieurs secondes avant d'afficher Connection timed out. Quelle est la cause la plus probable ?

      Réponse

      Un pare-feu (local sur srv-bdd via ufw/firewalld/iptables, ou un pare-feu réseau/Security Group entre les deux serveurs) bloque silencieusement (DROP) les paquets TCP à destination du port 5432.

      6.4 Si telnet 10.20.30.40 5432 affiche Connected to 10.20.30.40., mais que le programme Java échoue toujours, que pouvez-vous en déduire ?

      Réponse

      La connectivité réseau, le pare-feu et l'écoute du service sont 100 % fonctionnels. Le problème est purement applicatif / d'authentification (mauvais mot de passe, nom de base erroné, autorisation IP manquante dans pg_hba.conf, ou problème de certificat TLS).

    7. Quelle option de netstat permet d'inspecter les erreurs matérielles, pertes de paquets et débordements (ERR, DRP, OVR) d'une carte réseau ?

      Réponse 
      $ netstat -i
